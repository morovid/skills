# Implement a feature

The lead owns sequencing, integration, and requester communication. Implementation workers own changes and author evidence; [review](../review/SKILL.md) owns independent findings and verdicts. Use stronger agents/models for coordination, complicated cross-cutting implementation, and independent verification; use the smallest capable agents for exploration, scoped edits, and established commands. When the host does not expose model choice, use available agent types and narrow their assignments. If nested delegation is unavailable, the lead dispatches scoped tasks and relays results.

## 1. Start at the earliest missing or invalid handoff

- For an end-to-end request, load and run the missing or affected skills in order: [spec](../spec/SKILL.md) for intent and **Ready for engineering**; [plan-code](../plan-code/SKILL.md) for design and **Ready for implementation**; [plan-tests](../plan-tests/SKILL.md) for coverage and **Ready for test implementation**. Resume directly here when all three handoffs qualify. Stop at a requested stage boundary; do not broaden a planning-only request into implementation.
- Before editing, locate the exact **Current** spec with its reviewed package index and both plans with matching full independent **PASS** reports, linked designs, and applicable baselines. Accept equivalent artifacts that meet the same conditions. Reuse unchanged passed work; don't rerun a review merely because this skill loaded it. Record source versions, repo rules, starting revision and local changes, scope, execution access, and any material drift. Preserve unrelated work and keep evidence/report files outside the implementation snapshot. If a necessary upstream skill, authority, or input is unavailable, name the affected work and exact next action rather than infer behavior or bypass readiness.
- On resume, read the [implementation record](assets/implementation-record-template.md), actual diff, review reports, prior responses and execution evidence. Verify which steps and checks still apply to the current snapshot before resuming; retain incomplete and failed outcomes.

## 2. Implement and integrate by dependency

1. **Dispatch work from the plans.** Schedule production tasks and test work together using their IDs and dependencies. Establish shared interfaces and fixtures before dependent work, or write a planned regression test first when it can exercise the intended behavior. Run independent assignments in parallel only with non-overlapping edits; use one writer per file/worktree where edits overlap. Give each worker exact plan/spec/case locators, scope and exclusions, prerequisites, file ownership, allowed commands, and expected observable completion. Use a stronger implementation owner where integration or ambiguity demands judgment. If no suitable helper is available, the lead can do bounded author work; record authorship and never use that work as independent review.
2. **Integrate and record the actual changes.** Inspect the diff against the assigned scope and record completed tasks, changed paths, authors, deviations, and outstanding work. Leave unrelated edits intact. Keep each requirement and planned test oracle authoritative at its source; don't change a correct assertion to make faulty behavior pass. A local mechanical adjustment consistent with confirmed commitments can be logged; a material behavior/scope gap goes to `spec`, a production design/contract gap to `plan-code`, and a coverage, oracle, or observation-boundary change to `plan-tests`. Reopen the earliest affected skill and revalidate dependent plans before changing affected implementation. Continue unaffected work when safe.
3. **Run author checks once per applicable baseline.** Run the prescribed completion, acceptance, and regression checks (including existing-check or inspection-only dispositions); reuse inspectable matching CI evidence when permitted instead of duplicating execution. Record exact command or inspection, snapshot, environment, actual selection and result, log/evidence locator and limitations. Distinguish failures and skipped or unrun checks. Preserve first failures, identify product/test/environment blockers, and run affected checks after fixes. Do not edit baselines or waive failed checks without established authority. Author execution proves only what ran, not review or release readiness.

## 3. Submit to independent review and resolve returns

- Save `implementation-record.md` beside the code plan by default, using the template as a handoff index, not a second plan or review report. Pin the exact submission including relevant local changes, dependencies, configuration and fixtures. Supply the record, reviewed packages, change boundary, author identities, actual check evidence and any known gaps to `review`. If the request stops before review, return the snapshot and mark it **Awaiting review**, not reviewed. When useful, let review assess unaffected areas despite a known blocker; keep the blocked outcomes explicit.
- On **REVISE** or **BLOCKED**, route available fixes and unblock actions to the assigned authors or earliest owning skill. Carry out authorized corrections or revalidation that can proceed now, including refreshing stale plan handoffs. Pause only the work that depends on a still-unavailable prerequisite; name the owner and exact unblock action. Record finding IDs, responses, changed paths/versions, and new check evidence, then send the changed or newly supported submission to `review` for fresh independent rechecks. Keep the attempt history in the review reports and honor their stalled-loop decisions. Do not rerun an unchanged blocker or close findings as the author.
- Finish as **Implementation reviewed** only when planned work and prescribed checks are accounted for and `review` has a full **PASS** that is **Current** for the exact submitted snapshot. Otherwise report remaining work, review status, partial evidence, and what happens next. Return the snapshot, changed paths, implementation record, check summary, and linked review. No status here authorizes merge, release, or deployment.
