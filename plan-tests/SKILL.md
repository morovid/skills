# Plan Tests

The lead coordinates; a distinct test planner owns coverage and revisions; specialists design only justified categories; independent Test Analysis determines readiness. Use stronger agents/models for coordination, substantial design decisions, and independent verification; use the smallest capable agents for bounded searches, file reads, and mechanical edits. Do not write tests, change upstream artifacts, or approve baselines. The [Tests phase of review](../review/references/tests.md) checks implemented tests, not this plan.

## 1. Establish or resume the baseline

- Read the [spec](../spec/SKILL.md) package: `engineering-specification.md`, `review-report.md` (package index), linked catalogs, evidence, and the canonical D/A/Q register. It must be **Ready for engineering** and **Current** for the exact included versions. Read the [plan-code](../plan-code/SKILL.md) plan and linked material: **Ready for implementation** and **Current**, with a matching full independent **PASS** on that plan, spec package, and applicable repository baseline. A diagnostic checkpoint does not qualify. Accept equivalent or legacy artifacts with the same authority, readiness, and scope; require approval only where mandated.
- The specification governs required outcomes and expected results. The production plan describes intended logic, paths, seams, contracts, and dependencies; neither it nor the existing code can override confirmed behavior. Read applicable repository instructions, implementation and test conventions, relevant code/consumers, fixtures, and test/CI configuration. Record the revision or reproducible snapshot, relevant local changes, access limits, and drift. Distinguish current implementation, proposed changes, and work already implemented. Check material drift against the sources; return mismatches to the owning phase.
- On a return, read the current test plan, linked designs/evidence, saved review rounds, exact reviewed versions, prior responses, and changes since review. Accept legacy `test-implementation-plan.md` and its matching `review.md` as inputs. A legacy `test-analysis.md` may seed coverage and risk discovery after revalidation; neither it nor a legacy coordinator review is an independent verdict. Resume the earliest affected phase, reuse demonstrably unchanged work, and preserve the history. Reuse an already completed gate only if its roles, scope, and exact current baseline match.
- Preserve inherited spec, review, and code-plan IDs, as well as `TA` (scope), `TC` (existing coverage), `TR` (risk), `TD` (design work package), and `TB` (testability). Follow established conventions or use `TA1`/`TC1`/`TR1`/`TD1`/`TB1`, `TEST-<type>-<number>` for cases, and `WORK-1` for implementation tasks. Continue sequences and keep supersession links. Link the canonical decisions; never create a competing D/A/Q register or assume missing behavior.
- Resolve factual questions from available sources first. The lead routes objective/scope gaps to `spec` intake, baseline/impact/behavior/decision gaps to discovery, requirements/AC/DoD gaps to refinement, and package/readiness discrepancies to the review phase of `spec`. Route infeasible or inconsistent implementation designs and missing material test seams to `plan-code`. Record affected IDs, owner, and exact unblock action; continue independent work with dependent content visibly provisional. Only the lead raises requester questions.

## 2. Loop: plan → independent Test Analysis → revise

1. **Delegate test planning.** Launch a distinct test planner with [the planning guide](references/coverage-planning.md), [plan template](assets/plan-tests-template.md), and a self-contained handoff: assignment boundaries, versioned spec and production plan/reviews, repository instructions and snapshot, output paths, and any prior plan/review with changed IDs and closure conditions. The planner owns scope, cases through specialist delegation, consolidation, and responses. Keep one plan as the versioned index for linked designs and evidence. Add a [coverage evidence appendix](assets/coverage-evidence-template.md) only if useful; no separate inventory or gate is required.
2. **Use smaller agents for bounded work.** Where supported, the planner, specialists, and reviewers delegate independent searches, source tracing, existing assertion/CI inspection, and evidence collection to smaller read-only agents in parallel. Give each a narrow question and scope; ask for exact locators, evidence status and limits, what was read versus run, and conflicts. The owner verifies material claims at source; pass locators, not an author's interpretation as fact. Use smaller editing agents for separable mechanical edits or bounded drafting in named planning sections/files; assign non-overlapping work with one writer per artifact at a time and reconcile their output. Editing contributors are authors, not reviewers. Helpers cannot edit code, tests, configuration, specs, the production plan, or review verdicts. If lightweight helpers are unavailable, the owning agent handles the bounded work; this does not remove required role separation.
3. **Map coverage and assign designs.** The planner assesses affected areas, impacted consumers, current assertions, gaps, change risks, and testability. Classify each area as **Verification only**, **Existing coverage sufficient**, **Focused testing**, or **Comprehensive testing**. Inspect test bodies, mocks, fixtures, and selection rules before relying on existing tests. Record claim statuses (**Observed**, **Supported**, **Reported**, **Inferred**, **Unknown**) with locators and limits. Run existing checks only if authorized and useful to resolve uncertainty; record the actual command, snapshot, environment, outcome and limits, or **Not run**. Use the specialist procedure below for new or changed designs; no specialist is required if existing checks or inspections suffice. A no-new-test plan still needs concrete checks, evaluation criteria, and a residual-risk rationale.
4. **Reconcile and submit.** Apply the planning guide's reconciliation: map required outcomes and material implementation paths separately, link authoritative cases rather than copying them, and sequence work around interfaces, setup, and completion evidence. The planner self-checks completeness and submits **Ready for test plan review** only when required designs are complete and material design blockers resolved. Bounded execution prerequisites may remain. The lead checks that the saved handoff is complete, not whether the plan passes.
5. **Run Test Analysis independently.** For the initial review and every recheck, launch a stronger reviewer in a new session, distinct from the lead, plan authors, planning evidence helpers, and any prior reviewer session. Provide [the review procedure](references/test-analysis-review.md), exact plan and supporting versions, upstream packages, repository snapshot and rules, change boundary, identities, prior responses, and report path. Use saved artifacts, not transcripts. The first review covers the whole plan; rechecks verify changes, dependencies, and closure, carrying forward only demonstrably applicable evidence. The reviewer owns the saved report, not the plan. If independent review is unavailable, preserve progress and report the blocker; never substitute a self-check.
6. **Act on the saved verdict.** The lead verifies the report's independence, scope, baseline, and current verdict. A full **PASS** makes that version **Ready for test implementation** without another gate. On **REVISE**, return stable findings and closure conditions to the planner and owning specialist or upstream phase. Record corrections, changed versions, or evidence-based disagreements and resubmit to a fresh reviewer. On **BLOCKED**, continue unaffected work and pause until the prerequisite changes. Keep one review attempt history and apply the review procedure's stalled-loop guard.

### Delegate category designs

- Launch one actual specialist agent per justified test type needing new or changed design; split mixed `TD` packages without changing IDs. Use [unit](references/unit.md), [integration](references/integration.md), [E2E](references/e2e.md), [component](references/component.md), [visual](references/visual.md), or [other specialist guidance](references/specialist.md) (e.g. accessibility, security, performance) as applicable, not as separately installed skills. Keep component and visual distinct. Use the least costly reliable level; add another only for a distinct observation or mandated assurance.
- Give each specialist its category, assigned IDs and priorities, exact spec/plan/evidence locators, intended paths and boundaries, existing-test actions, exclusions, adjacent ownership, and known constraints or unresolved blockers. Provide [the category](assets/category-design-template.md) and [case templates](assets/test-case-template.md), case prefix, and an exclusive output such as `unit.md` or `<type>.md`. Keep cases authoritative in those files; link them from the plan. Run independent assignments in parallel where supported and queue remaining types rather than dropping or combining them. Specialists report addressed packages, case IDs, discovered risks, evidence limits, and blockers; the planner inspects actual work before accepting it.
- If nested delegation is unavailable, the planner or reviewer supplies scoped specialist or helper assignments; the lead dispatches them and relays their outputs within the same round. Missing required specialist capability blocks only the dependent designs; the lead does not substitute for the specialist.
- Cases need concrete setup, meaningful partitions, actions, sourced and observable assertions, actual versus simulated boundaries, deterministic controls, and grounded execution instructions. Use **Retain**, **Extend**, **Modify**, **Replace**, and **Run for regression** for existing checks, **Create** for new cases, and **Verification only** for inspection actions. Replacements must preserve still-required obligations; a test title or coverage percentage does not establish which assertions pass. Missing future setup may be a task; an unknown material expected outcome or feasibility choice is a design blocker.

## 3. Save, revalidate, and hand off

Use the requested destination or assignment convention; otherwise save `plan-tests.md`, `plan-tests-review.md`, and selected category files in `plan-tests/` beside the engineering specification (or in the assignment working directory if it has no specification file). Inspect existing outputs before editing, preserve identity and history, remove placeholders, and state unknowns explicitly.

Track **Current** / **Needs revalidation** separately from stage status:

- **In progress:** investigation, design, or revision continues.
- **Ready for test plan review:** the current submission is complete and author-checked.
- **Blocked at test planning:** a material gap prevents progress before a valid checkpoint; name the blocked phase and the required action. When blocked after a valid checkpoint, retain it and report what prevents the next phase.
- **Ready for test implementation:** the exact plan, linked designs, source packages, and relevant repository baseline have a current full independent **PASS**.

Changes to relevant spec, production plan, test design, tasks, or material assumptions about code/tests/CI invalidate affected checkpoints and downstream handoffs. Mark them **Needs revalidation** and record changed versions/IDs and required checks even when downstream files cannot be edited. Expected edits that implement the approved designs do not alone invalidate the plan. Restore readiness after an independent pass on the new baseline. Updating readiness metadata or a link to the matching review does not change technical content.

Return plan and review paths/versions, applicable category outputs, readiness and currency, and next action or blocker. Hand the current package with the spec and code plan to [implement](../implement/SKILL.md). A ready plan does not establish implemented coverage, passing tests, approved visual baselines, or release readiness.
