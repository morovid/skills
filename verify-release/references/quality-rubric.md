# Release gate quality rubric

For a full gate assess every row and every registered mandatory subcheck as Pass, Fail, Not assessed, or justified Not applicable. Conditional content follows actual architecture, confirmed requirements, and established release policy. Missing evidence is Not assessed, not non-applicability. Do not invent numeric thresholds, mandatory tools, or exception authority.

| Check | Pass condition |
| --- | --- |
| RG1 — Candidate identity and integrity | Exact source snapshot/local changes, dependency locks, relevant toolchain/build configuration, target environment, and immutable release artifact where applicable are pinned. Evidence links reviewed/tested inputs to the actual payload; mutable identifiers or unexplained artifact differences are insufficient. Identity still matches at gate completion. |
| RG2 — Authority and upstream reviews | Current specification, reviewed implementation plan, test analysis/design, and full independently passed code/test/security reviews cover the candidate and required scope. Material differences, finding dispositions, required approvals, and review limits are reconciled by their owners; no self-check or limited review substitutes for a required gate. |
| RG3 — Required test execution | Every required suite, shard, case selection, and environment completes successfully under established criteria. Discovery/selection and skip/exclusion evidence establish that intended tests actually ran. Missing suites, zero-test success, unapproved exclusions, unresolved failures, and unexplained retry-only passes do not satisfy the condition. |
| RG4 — Build and code quality | The production build/package succeeds from the pinned inputs using the intended configuration. Applicable type checks, linting, static analysis, and established quality budgets pass without auto-fixes, baseline changes, new suppressions, or check weakening. Generated artifact identity and any required build provenance are recorded. |
| RG5 — Security evidence | Current security review covers actual code/dependency/configuration/exposure. Required secret/dependency/source/container/infrastructure or other applicable checks pass, advisory evidence meets required freshness, and new findings receive owner dispositions. A clean scanner result cannot replace review, and required security failures cannot be hidden in suppressions. |
| RG6 — Acceptance and regression | Every current in-scope requirement/material AC, B Add/Change/Remove/Preserve obligation, significant I dependency, and applicable DoD outcome reaches adequate existing review/execution/inspection evidence or a justified disposition. Critical required journeys and regression checks cover the actual candidate and required boundaries. No material plan/spec discrepancy or open Blocking/Major finding remains. |
| RG7 — Non-functional conditions | Applicable performance, resource, accessibility, reliability, and compatibility requirements pass using their sourced measurement methods, environments/workloads, budgets, and baselines. Missing required metrics are not silently replaced with guesses or broad coverage scores. |
| RG8 — Deployment, data, and recovery | Applicable configuration/secrets prerequisites, platform/dependency compatibility, migration and mixed-version behavior, backup/recovery needs, and rollback or forward-recovery procedures are feasible and evidenced to the required depth. Any required rehearsal is complete; destructive data changes are not assumed reversible. |
| RG9 — Operations and rollout readiness | The actual distribution/deployment model has a responsible owner, required health/monitoring signals, staged rollout where applicable, concrete stop/recovery conditions, and planned post-release verification. Service checks are justified as inapplicable for other product types; future production health is not claimed as observed. |
| RG10 — Delivery, approvals, and gate integrity | Applicable documentation/release notes/operator instructions and DoD obligations are complete. Only mandated approvals are required and their candidate scope is verified. Exact evidence, limitations, findings/owners/closure, history, readiness, currency, and downstream revalidation are recorded; no mandatory failure is traded against unrelated passing metrics. |

## Evidence reuse and counterexamples

Existing CI evidence is reusable only when its run identity, source/artifact, commands/configuration, target environment, complete selection/results, and freshness match the registered check. Reuse of planning evidence also needs reconciliation of relevant assumptions. A pass for yesterday's commit or another environment is not evidence for this candidate without demonstrated equivalence and applicable owner revalidation.

Check realistic ways a nominally green release could be invalid: a test job filtered out integration cases; a retry hid an unresolved failure; packaging rebuilt a different artifact; a security scan used a different lockfile; a migration broke rollback; a required monitor lacks a usable signal. Record defects only when evidence establishes them; otherwise identify the missing check and exact unblock action.

This gate consumes review judgments and verifies release evidence. It cannot close SEC/CR/TREV or other upstream findings on the owner's behalf, manufacture independent review, waive failed requirements, or execute production rollout merely because all checks pass.
