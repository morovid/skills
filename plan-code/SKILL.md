# Plan Code

The lead coordinates; a distinct planner owns the design, tasks, and responses; one independent review loop determines readiness. Use stronger agents/models for coordination, substantial design decisions, and independent verification; use the smallest capable agents for bounded searches, file reads, and mechanical edits. If nested delegation is unavailable, the lead dispatches scoped helper assignments and relays their results. Do not implement production code, write test cases, or change authoritative specifications.

## 1. Establish or resume the baseline

- Accept a [spec](../spec/SKILL.md) handoff, its directory, or either entry artifact: `engineering-specification.md` or `review-report.md` (the package index). Locate the matching package and follow its linked catalogs, evidence, and canonical D/A/Q register. Accept older `spec-review` handoffs and equivalent artifacts with the same authority and detail. **Ready for engineering** and **Current** must cover the exact included versions. A draft, partial assessment, stale verdict, or **Ready for review** does not qualify. Check only approvals actually required by the assignment.
- Read applicable repository instructions and record the revision or reproducible snapshot, relevant local changes, access limits, and any drift from specification discovery. Recheck material drift against the sources; the repository cannot silently override confirmed behavior. Record the sources, versions, canonical decision location, and limits in the plan.
- On a return, read the current plan and supporting files, the review report, exact reviewed versions, prior responses, and changes since review. Accept legacy `implementation-plan.md` and `implementation-review.md` as inputs. Resume the earliest affected work and preserve history. Reuse a completed full **PASS** only when its independence, scope, and exact current baseline still qualify; a diagnostic checkpoint does not qualify.
- Preserve inherited E/CB/I/B/D/A/Q/US/SC/FR/NFR/AC and RV/RW IDs and meanings. Follow assignment conventions; otherwise use `DES-001` for design, `DEC-001` for internal technical choices, and `IMP-001` for tasks. Preserve sequences and supersession links. Technical choices cannot create product behavior or replace canonical decisions.
- Resolve factual questions from available sources first. The lead routes objective and scope gaps to `spec` intake, baseline/impact/behavior/decision gaps to discovery, requirements/AC/DoD gaps to refinement, and package/readiness discrepancies to the review phase of `spec`. For unresolved authority, access, or decisions, record affected IDs, owner, and exact unblock action; continue independent work with dependent content visibly provisional. Do not fill product gaps by assumption.

## 2. Loop: plan → independent review → revise

1. **Delegate planning.** Use the host's agent tool to assign a distinct planning agent. Give it [the planning guide](references/planning-guide.md), [the plan template](assets/plan-code-template.md), and a self-contained handoff: assignment boundaries, versioned spec sources and decisions, repository instructions and baseline, output path, and any prior plan/review with changed IDs and closure conditions. Have it propose the smallest coherent design that fits the existing project and produce ordered, actionable tasks. Trace all material obligations to design/tasks or evidenced **No code change** dispositions; reverse-check unsupported work. The planner records actual versus proposed checks and flags testability concerns for `plan-tests` without designing cases.
2. **Use lightweight helpers for bounded work.** Delegate substantive file discovery, tracing, and evidence collection to smaller read-only agents where supported, in parallel for independent scopes. Ask for precise locators, evidence status and limits, what was inspected or run, and conflicts. The planner and reviewer independently verify material claims at source; pass locators, not a planner's interpretation as fact. Use smaller editing agents for separable mechanical edits or bounded drafting in named plan sections or supporting planning files. Assign non-overlapping edits with one writer per artifact at a time, have the planner reconcile the returned edits, and count contributors as authors, not reviewers. Helpers must not edit product code, tests, configuration, specs, or review verdicts. If lightweight helpers are unavailable, the owning agent handles the bounded work; this does not remove role separation.
3. **Submit the saved plan.** The planner checks its own work for completeness and consistency and marks it **Ready for implementation review**. The lead checks that the handoff is complete, not whether the plan passes. Provide exact paths/versions, change boundary, repository snapshot and local-change scope, author identities, applicable rules, prior responses, and the report path. Use saved artifacts, not session transcripts.
4. **Review independently.** For the initial review and every recheck, launch a stronger reviewer in a new session, distinct from the lead, plan authors, planning evidence helpers, and any prior reviewer session. Use [the review procedure](references/review.md): the first review covers the whole plan; subsequent reviewers verify changes, finding closure, and dependent checks, carrying forward only demonstrably applicable evidence. The reviewer owns the saved report and never edits plan content. If no independent review can be completed, save progress and report the exact blocker; never substitute a self-check.
5. **Act on the saved verdict.** The lead verifies the report's independence, scope, baseline, and current verdict. A full **PASS** makes that version **Ready for implementation** without another gate. On **REVISE**, return stable findings and closure conditions to the planner; record the fixes, changed versions, or evidence-based disagreements and resubmit to a fresh reviewer. On **BLOCKED**, continue unaffected work and pause the affected path until the prerequisite changes. Keep one review attempt history and apply the [stalled-loop guard](references/review.md#recheck-findings-and-stop-stalled-corrections).

## 3. Save, revalidate, and hand off

Use the requested destination or assignment convention. Otherwise save `plan-code.md` beside the engineering specification (or in the assignment working directory if no specification file exists) and `plan-code-review.md` beside the plan. Keep one plan as the versioned index for any linked supporting files. Inspect existing outputs to preserve assignment identity and history; remove template placeholders and state unknowns explicitly.

Track **Current** / **Needs revalidation** separately from stage status:

- **In progress:** investigation, planning, or revision continues.
- **Ready for implementation review:** the current submission is complete and author-checked.
- **Blocked at implementation planning:** a material gap prevents progress before a valid checkpoint; name the blocked phase and the required action. When blocked after a valid checkpoint, retain it and report what prevents the next phase.
- **Ready for implementation:** the exact technical plan, source package, and relevant repository baseline have a current full independent **PASS**.

Source, design, task, or material repository changes invalidate affected checkpoints and downstream handoffs. Mark them **Needs revalidation** and record changed versions/IDs and required checks even when downstream files cannot be edited. Expected edits that implement the approved design do not alone invalidate the plan; material changes to its assumptions or commitments do. Restore readiness only after an independent pass on the new baseline. Updating only readiness metadata or a link to the matching review does not change the reviewed technical content.

Return the plan and review paths/versions, readiness and currency, and next action or blocker. Hand the current package to [plan-tests](../plan-tests/SKILL.md) for coverage design and then to [implement](../implement/SKILL.md) with the reviewed test plan. Material production-plan feasibility findings return to `plan-code`. Readiness is not completed implementation, passing tests, or delivery acceptance.
