# Security review quality rubric

For a full gate assess every row as Pass, Fail, Not assessed, or justified Not applicable. A row may contain several controls: record distinct results where coverage differs. Inapplicable controls need a reason tied to actual architecture/exposure; missing access or evidence is Not assessed. Extend with sourced assignment obligations without inventing thresholds or universal tooling requirements.

| Check | Pass condition and inspection focus |
| --- | --- |
| SR1 — Authority and baseline | Current specification, reviewed plan, canonical decisions, applicable security policy, repository/local-change boundary, relevant dependency/configuration versions, independence, and mandated approvals are established. Material drift and assumed deployment conditions are reconciled. |
| SR2 — Security obligations and plan conformity | Every in-scope security FR/NFR, material AC, B obligation, significant I dependency, and applicable DoD outcome reaches inspected control/verification evidence or justified non-applicability. Security-relevant DES/DEC/IMP commitments and deviations have explicit dispositions; no implementation choice silently changes authority. |
| SR3 — Threat coverage and reachability | Relevant assets, attacker capabilities, entry points, trust boundaries, sensitive flows, indirect consumers, and external dependencies are mapped. Plausible abuse paths, inherited exposure, preserved/removal protections, and relevant pre-existing weaknesses are assessed with scope limits; missing specification language does not conceal demonstrated vulnerabilities. |
| SR4 — Identity, authorization, and isolation | Applicable authentication, credential lifecycle, sessions/tokens and revocation controls hold. Server-side object/action/role/tenant authorization covers relevant routes, background tasks, and alternate paths with safe denials and no unauthorized side effects. Relevant CSRF and cross-origin controls preserve the intended browser trust boundary. |
| SR5 — Untrusted input and dangerous operations | Attacker-controlled data cannot cross relevant execution, query, template, serialization, or output boundaries unsafely. Applicable injection/XSS, unsafe deserialization, path traversal, upload, redirect, and outbound-request/SSRF paths have effective protections at the correct boundary, including bypasses through encoding, redirects, or indirect consumers where relevant. |
| SR6 — Sensitive data, secrets, and cryptography | Relevant secrets and personal/sensitive data are protected in storage, transport, logs, errors, caches, artifacts, and external services. Key/token handling and cryptographic choices fit actual security requirements and supported platform capabilities; exposed credentials receive appropriate containment/rotation evidence from their owner, not just source removal. |
| SR7 — Abuse, state, and availability | Relevant business operations resist authorization bypass through ordering, replay, races, retry, or partial effects. Applicable rate, resource, timeout, and size constraints protect exposed operations against credible abuse under established requirements; safe failure/cleanup preserves protection without inventing new product limits. |
| SR8 — Dependencies, build, and deployment exposure | Actual resolved dependencies, relevant advisories, build inputs, CI permissions/untrusted contributions, container/IaC settings, and deployment defaults are assessed where applicable. Privileges, debug/admin surfaces, network exposure, and security configuration fit the intended environment. Findings/suppressions have evidence and required policy dispositions; missing production evidence is explicit. |
| SR9 — Verification and evidence quality | Appropriate static inspection, negative/security tests, scans, and bounded reproductions substantiate the required controls and realistic bypass assessment for this snapshot. Tool configuration, advisory freshness, execution targets/results, failures/skips, and limits are explicit. Existing test success or clean scanner output does not substitute for threat/control review. |
| SR10 — Findings, closure, and review integrity | Findings distinguish demonstrated weaknesses, unconfirmed concerns, missing evidence, and optional hardening. Severity, confidence, owners, authority for any permitted exceptions, verified closure, version-bound history, and downstream revalidation are recorded. No material issue is hidden as later release work. |

## Counterexamples and evidence

For each material trust boundary, follow an attacker-controlled value or identity to the protected operation. Identify the enforcement point, whether alternate consumers bypass it, and the observable denial or safe effect. For example, an authenticated endpoint can still omit object ownership enforcement; a URL allowlist can still permit an unsafe redirect; a dependency can be present without an exposed vulnerable feature. These are prompts for evidence, not findings by themselves.

Separate a required control absent from code, a realistic exploit path, a threat that existing controls demonstrably stop, and an unresolved environment assumption. Lack of runtime access does not erase a demonstrated code defect; static reasoning alone must not be reported as an executed exploit. Record precisely what a reproduction, assertion, or scanner actually establishes.

An external standard can supply a control catalog when applicable; record its exact version and selected controls. This review does not assert blanket compliance or require every security category for a change with no relevant exposure.
